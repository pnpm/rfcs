# Shared side-effects cache

## Summary

pnpm already caches the result of a dependency's build so it does not have to run again. That cache is local to one machine. This RFC makes it shareable for the subset of packages where sharing is sound: pnpm may fetch a package's *built* form instead of running its install scripts, signed either by the organization whose CI produced it or by the package's own publisher. Artifacts travel over an openly documented protocol, gated by explicit opt-in and verified by signature rather than by the channel that served them, with pnpr as the reference implementation.

> **Status: partially implemented.** An opt-in proof of concept landed in [pnpm/pnpm#14171](https://github.com/pnpm/pnpm/pull/14171) and shipped in pnpm v12.0.0 alongside pnpr 0.1.0-alpha.8, in both the TypeScript and Rust stacks. It implements organization mode over pnpr's `v0` artifact endpoints, on Linux/glibc only. Sections below carry **Shipped in v0** notes recording what the implementation confirmed, what it settled that this document had left open, where it deliberately narrowed the design, and what remains deferred. The narrowings are scope, not disagreement; the one place the shipped shape diverges from what this document specifies — how lookups are batched — is called out where it occurs.

## Motivation

Every CI runner, every fresh container, and every new laptop re-runs `node-gyp` for the same native module. The work is usually redundant, and pnpm already detects the common case: it computes a dependency-state key and skips the rebuild whenever the same machine has seen those inputs before. The result is simply not portable.

This is the one capability a Nix binary cache offers that pnpm has no answer to. It surfaced concretely in [pnpm/pnpm#13639](https://github.com/pnpm/pnpm/pull/13639), which proposed delegating package materialization to an external `packageProvider` executable in order to reach it (closing [pnpm/pnpm#11703](https://github.com/pnpm/pnpm/issues/11703)). That approach obtains shared build outputs at the cost of a second install mode in which pnpm's build allowlist, global virtual store, hoisting, and the Rust fast path are all bypassed, and in which a new stdio protocol becomes a permanent compatibility surface.

The underlying need does not require any of that. pnpm already has the cache, a key, and the payload format. What it lacks is a transport, a trust model, and — the substance of this RFC — a defensible answer to when a build output may be shared at all.

Tracking issue: [pnpm/pnpm#13771](https://github.com/pnpm/pnpm/issues/13771).

### What already exists

- **A dependency-state key.** `calcDepState` (`pnpm11/deps/graph-hasher/src/index.ts`) produces `${platform};${arch};node${major}` plus `;deps=<graph hash>` and `;patch=<hash>`. It captures the dependency graph, applied patches, OS/arch, and the Node major that will spawn the script. It still does, and still keys the local cache; the portable key specified below now lives beside it as `calcDepStateInputKey` rather than replacing it.
- **A payload that is already a diff over content-addressed files.** `sideEffectsMaps?: Map<string, { added?: FilesMap, deleted?: string[] }>` (`pnpm11/store/cafs-types/src/index.ts:28`). Every added file is an ordinary CAS entry, so a manifest is `(path, digest, mode)` triples plus deleted paths.
- **Separate read and write settings.** `sideEffectsCacheRead` and `sideEffectsCacheWrite` (`pnpm11/config/reader/src/Config.ts:151-152`).
- **A build allowlist that already covers cached builds.** Since [pnpm/pnpm#11039](https://github.com/pnpm/pnpm/pull/11039), `allowBuild` is consulted for packages that would otherwise be skipped as already built (`pnpm11/building/during-install/src/index.ts:119,149`). This RFC must preserve that gate, not reintroduce it.

## Detailed Explanation

### The build-input problem

**The dependency-state key is not a function of everything a build depends on, and for arbitrary npm packages it cannot be made one.**

This is the central constraint, and it is easy to understate. `calcDepState` captures the dependency graph, patches, OS, arch, and Node major. A lifecycle script may additionally depend on environment variables, compiler and linker versions, the C++ standard library, Python, platform SDKs, system headers and shared libraries, CPU feature detection, network responses, the wall clock, and arbitrary files on the host. libc is one known omission; it is not the only one, and enumerating the rest is not a finite task.

The consequence is that two honest builders can produce materially different outputs under the same key. A cache that assumes otherwise is not merely inefficient — it silently serves the wrong artifact. This is precisely where the Nix analogy breaks down: Nix can treat a store path as a pure function of its inputs because it *models* the inputs and builds in a restricted environment. npm install scripts do neither.

### Bounding the problem instead of closing it

The input set cannot be closed for arbitrary npm packages, so this RFC does not try to. It bounds the blast radius instead, by three means — none of which is cache-key fragmentation.

**A named owner, who accepts the residual risk.** Every artifact traces to a party that owns its correctness — an organization for artifacts its own CI produced, or a package's publisher for artifacts it ships with its releases. If two of Acme's builders disagree about how to compile a package, that is Acme's inconsistency to fix, and Acme is positioned to notice and fix it; if a publisher's binary is wrong for a platform it claimed, the publisher is. This is the same bargain Turborepo, Nx, and moon make for their own artifacts, and it is why they need no environment model at all. It is also why this RFC declines an *anonymous, multi-builder* public cache, where anyone may contribute an artifact for anyone's package: there the residual risk has no owner, and the mechanisms that would be needed instead — reproducibility or attestation — are a different and much larger project. A cache whose artifacts carry a named owner is a different proposition entirely — that is publisher mode, specified next and fully in scope.

**Compatibility constraints, which are the hard gate.** What actually has to be enforced per artifact is not "was this built in an environment I approve of" but "will this run correctly here". That is what the compatibility tags in the next section do, and they do it as floors, so an artifact built against an older libc stays valid on newer systems — including when the builder's own image is patched.

**A package eligibility contract.** Sharing is opt-in per package, not blanket, and the default for a package nobody has vouched for is to build locally. Eligibility may be asserted by the publisher, by the registry operator for packages they have evaluated, or by the consuming organization for its own dependencies. This is where packages that are inherently unshareable are excluded — those whose builds read the clock, the network, or the host's mutable state — and no key design substitutes for it.

**The builder profile is provenance, not a key component.** An artifact records the environment it was produced in: a container image digest, the target architecture baseline, and the build environment as a **canonical name-to-value map**, with every undeclared variable denied. Names alone are insufficient — `CFLAGS=-march=x86-64` and `CFLAGS=-march=native` satisfy the same allowlist and produce artifacts that are not interchangeable. Variables carrying secrets are denied rather than recorded, since provenance is served to clients and a name allowlist that merely permits them would leak them.

A flag such as `-march=native` makes the produced artifact's real requirements unknowable from the environment alone, which is a *compatibility tag* problem rather than a profile one: such a build must either declare a correspondingly narrow architecture tag or be ineligible. The profile itself travels in the signed block for debugging, incident response, and optional organizational policy.

It deliberately does **not** participate in the input key. Doing so would fragment the cache along an axis that mostly does not affect correctness: a routine base-image security patch changes the digest and would invalidate every artifact built under it, in precisely the CI scenario the feature exists to serve. It is also a producer-side claim rather than a verifiable property — nothing in an artifact proves where it was built — so treating it as a correctness mechanism would overstate what it can carry. The signature makes the claim attributable; the compatibility tags are themselves a signed producer assertion, constraining where an artifact may be used rather than establishing that it is safe. Safety rests on the trusted builder and the eligibility contract.

**Sharing requires behavioural equivalence, not bit-identity.** Any artifact for input key K must work correctly on any machine matching its compatibility constraints. Embedded timestamps, link order, and hash-iteration nondeterminism are irrelevant. This is a materially lower bar than Nix's, and it is why the problem is tractable at all.

Finally, a *hermetic* sandbox with declared inputs — restricting filesystem reads, environment, network, clocks, and randomness — is the one thing that would genuinely close the input set rather than bound it. Plain sandboxing is not sufficient: [pnpm/pnpm#13772](https://github.com/pnpm/pnpm/issues/13772) is primarily about restricting authority and leaves network policy open, and a sandbox permitting network access closes nothing. Network is the largest gap in practice, since `node-gyp` fetches headers and `prebuild-install` fetches binaries, so hermeticity means `--network=none` plus pre-seeded caches — what Nix does, and what breaks packages unprepared for it. CPU feature detection is the second, which is why the architecture baseline is recorded. Nothing here depends on hermetic sandboxing shipping; it would allow the trust domain to widen later, and a hermetically sandboxed build is the strongest form of an eligible one.

### Two modes, one mechanism

There are two ways an artifact acquires an owner, and this RFC specifies both. They are not sequential designs; they are the same protocol with a different signer and a different party asserting eligibility.

**Organization mode.** A team's CI builds and signs artifacts for its own dependencies, and the organization owns their correctness within its trust domain. Fully deployable with pnpm and pnpr alone.

**Publisher mode.** A package's own publisher ships its built forms alongside its source, exactly as PyPI serves wheels next to sdists, and owns their correctness for every consumer.

**Owner scope is an explicit union, and it is what the signature binds.** The two modes are not distinguished by which host serves an artifact but by who owns it, so the protocol carries the owner as a tagged value rather than as a single tenant identifier:

- `organization` — scoped to a named trust domain. Valid only for consumers configured to trust that domain, namespaced under it in storage, and never shared across domains.
- `publisher` — scoped to a package identity. Valid for *every* consumer that trusts that publisher, namespaced under the package rather than under any consumer, and explicitly not tenant-scoped.

Every place the design previously said "tenant" means owner scope, and the two members behave differently on purpose: an organization artifact that escapes its domain is a bug, while a publisher artifact that reaches every tenant is the entire point. Collapsing them into one identifier — as an earlier draft of this RFC did — cannot express a publisher artifact at all.

Publisher mode is the more defensible of the two, not the more speculative. The trust relationship already exists: a consumer who installs a package already executes that publisher's install script, and accepting a prebuilt artifact signed by the same identity is a *smaller* grant than arbitrary code execution during install — the artifact is not executed during installation, though a native binary or generated JavaScript in it will of course run later when the package is used. It reuses an existing identity anchor rather than introducing one: the same publisher identity that already authenticates the package, for which [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/) and [npm provenance](https://docs.npmjs.com/generating-provenance-statements/) exist. That is an anchor, not a finished mechanism — trusted publishing authenticates CI to the registry, and provenance attests a particular *package* build, so artifacts need a new attestation subject and an authorization policy for who may attest artifacts on a package's behalf. Reusing the anchor avoids a new root of trust; it does not avoid that specification work, which is listed as unresolved below. And as Prior Art notes, the ecosystem already does this through `prebuild-install` and `node-pre-gyp`, without integrity pinning, signatures, or offline support.

**Publisher mode does not depend on any particular registry cooperating.** Because the publisher's signature is the authority, the distribution channel does not have to be trusted: an artifact may be served by the origin registry, by a mirror, by a proxying pnpr, or from wherever the publisher already publishes binaries today, and the client verifies the signature regardless. This is how Nix substituters and distribution mirrors work, and it is why publisher mode is not gated on `registry.npmjs.org` adopting anything. What it does require is **discovery** — a way for a client to learn where a given publisher's artifacts live — which is an open question below rather than a dependency on a third party.

Two consequences follow for the design, and both are settled here rather than deferred:

- **The signer is a pluggable trust root with both kinds defined.** Organization keys and publisher identity are peers in the protocol, not a primary and an extension.
- **The compatibility tag format is designed against publisher mode.** A team cache targets machines its operator knows and can correct in an afternoon; a publisher targets every consumer, so tag floors must be right the first time. A format built for the team case and stretched later would not reach — so the harder case sets the requirements, and organization mode simply uses a format that is more precise than it strictly needs.

Organization mode is expected to *ship* first, because it is entirely within pnpm and pnpr and is a smaller surface on which to prove the protocol. That is a rollout order, not a scope boundary.

**Shipped in v0.** It did ship first. The owner is a tagged value on the wire and both arms are parsed, but only `organization` is accepted: a `publisher` owner is rejected outright until discovery and the attestation policy below are specified, rather than being provisionally honoured. In the proof of concept an organization owner's name must equal the authenticated pnpr username, which is the smallest thing that makes the namespace real and is emphatically not the key-distribution answer. The tag vocabulary was nevertheless designed to publisher-mode requirements, as this section demands — the v0 glibc floors are more precision than a single team's cache needs.

### Compatibility tags are not the lookup key

An artifact built against glibc 2.17 should serve a glibc 2.39 machine. That is a floor, not an identity — and a floor cannot be expressed by hashing the consumer's own platform into the key it looks up. A 2.39 client would request a key containing 2.39 and never find the 2.17 artifact.

Two distinct concepts are therefore required:

- **An input key** identifying what was built: the dependency graph and applied patches. This is `calcDepState` with the platform components removed, and it is what an entry is stored under.
- **Compatibility constraints** the artifact advertises, as an explicit union: `universal`, a positive assertion that the output is platform-independent; or `tagged`, listing the platform tags it is valid on, expressed as floors where the underlying property admits one. There is deliberately no third state — an entry whose constraints are absent, malformed, or expressed in a vocabulary the client does not know is a **miss**, never a wildcard. Absence of information must not become permission, which is what an "optional tags" field would have quietly meant.

The client presents an ordered set of tags it supports and selects the best offered artifact, exactly as Python installers select among wheels rather than hashing the interpreter's exact identity into a filename ([PyPA platform compatibility tags](https://packaging.python.org/en/latest/specifications/platform-compatibility-tags/#use)). Two properties follow: an artifact serves many systems rather than one, and a tag the client does not understand is a miss, never a guess.

**Shipped in v0.** The vocabulary is deliberately one narrow tagged form — `pnpm:v1:linux-<architecture>-node<major>-glibc<major>.<minor>`, with `architecture` in `{x64, arm64}` and every numeric component a canonical unsigned decimal — plus `universal`. A consumer generates its glibc floors down to minor zero, most recent first, so a glibc 2.3 host advertises `glibc2.3`, `glibc2.2`, `glibc2.1`, `glibc2.0`; matching is then exact string membership in that ordered set, and a 2.1-floor artifact serves the 2.3 consumer without the client parsing version ranges it was never given. Tagged matches beat `universal`, and equal-rank variants are ordered by ascending signed-envelope digest so selection is deterministic rather than dependent on response order. Other platforms and libc families are simply absent from the vocabulary — the same "absence of information is not permission" rule applied to the vocabulary itself, since the alternative is a client guessing what a musl tag it has never seen implies.

**macOS vocabulary.** macOS adds a new form to the v1 vocabulary without changing the shipped Linux tags: `pnpm:v1:darwin-<architecture>-node<major>-macos<major>.<minor>`, again with `architecture` in `{x64, arm64}` and canonical unsigned decimal components. The macOS version is the product version, not the Darwin kernel release. Patch releases do not create a new compatibility boundary; `15.5.1` is represented as `macos15.5`.

The version in an artifact tag is a minimum runtime. A macOS consumer presents one tag containing its current product version, and an artifact matches when the schema, operating system, architecture, and Node major are equal and the consumer's `(major, minor)` pair is greater than or equal to the artifact's. When several variants match, the greatest minimum version wins; `universal` remains the final fallback. This makes the floor comparison explicit instead of expanding every historical macOS minor release into the consumer's tag list, which would make the fingerprint grow without bound as macOS releases accrue.

Organization-mode publication uses the builder's current macOS product version as the floor. That is conservative when the produced Mach-O files declare an older deployment target, but never broadens their claimed compatibility beyond the builder on which they ran. A future publisher tool may inspect every Mach-O deployment target and advertise an older floor, but it must not infer one merely from the SDK or toolchain version. If the product version cannot be determined, the client neither publishes nor restores a tagged macOS artifact.

The consumer platform fingerprint remains SHA-256 over its canonical supported-tag list. A macOS consumer therefore fingerprints its one exact tag, so changing macOS minor versions changes the fingerprint. Existing clients reject the unfamiliar `darwin` form as a miss, while v1 Linux matching and fingerprints remain byte-for-byte unchanged.

### Fetching

**The registry is the default channel; the signature is the authority.** An artifact is looked up at the registry a package resolved from, which is what makes per-registry auth, certificates, proxies, and the registry-qualified lockfile keys work unchanged. But acceptance turns on the signature, not on which host served the bytes — so a mirror, a proxying pnpr, or a publisher's own distribution point can serve an artifact the client will accept, and a registry serving one it cannot verify has gained nothing.

**Requests are batched per channel and issued in parallel.** An install may draw from several registries. The client groups candidates by concrete channel and sends each only its own candidates — both because no single origin could answer for all of them, and because broadcasting the full candidate set would leak an organization's cross-registry dependency graph to every registry it talks to.

Within a registry the lookup is one round trip for the whole install, mirroring how `POST /-/pnpr/v0/resolve` takes an entire workspace in a single request. This matters because the lookup sits immediately before the builds that are the last thing blocking install completion. Where the client is already talking to pnpr, the lookup should fold into the resolve request that is already happening, so a warm install pays no additional round trip at all.

Only packages marked `requiresBuild` are candidates — those declaring `preinstall`/`install`/`postinstall`, plus the implicit cases `pkgRequiresBuild` detects from `binding.gyp` or a `.hooks/` directory. When such a package is also patched, the patch hash is part of its input key. Packages that are *only* patched are deliberately excluded: applying a patch overlay locally is cheap, and including them would require inventing build-approval semantics for packages that have no build to approve, contradicting the `allowBuild` requirement below.

Candidates are identified by an **opaque key string** the client computed, not by a structured package identifier — see the forward-compatibility note below for why. Keys are domain-separated by a prefix naming the artifact kind and its version (`dependency-side-effects:v1:…`), and the signed envelope binds that kind, so a signature issued for one kind of artifact can never be replayed as another. A response carries, per candidate, the *set* of variants the registry holds: each with the `added` file list as `(path, digest, mode)` triples, the `deleted` path list, the compatibility tags, and the signed provenance described below. The client selects among variants on both compatibility and signer trust, so a registry holding several builders' output for one input key is a normal case rather than a conflict. Variants per candidate and total response size are capped by the client, since the response is untrusted input parsed before any signature is checked. Sending a diff rather than a built tree keeps responses proportional to what a build changed rather than to the size of the package.

**Clients MUST recompute the digest of every downloaded blob** before it enters the content-addressable store or the importer; the signed manifest attests the digests, but nothing attests that the bytes served match them. A mismatch is a cache miss and a diagnostic, and the offending entry is quarantined so the same poisoned artifact is not re-fetched on every subsequent install.

**Shipped in v0, with one divergence.** The endpoints are `POST /-/pnpr/v0/artifacts/resolve` (batch lookup, at most eight signed variants per key), `POST /-/pnpr/v0/artifacts/blob` (one owner-scoped blob per unique SHA-512, issuable in parallel), and `PUT /-/pnpr/v0/artifacts` (publication), all advertised through the existing handshake and mounted only when pnpr's `resolver.artifacts` is on, which it is not by default. Because the response is untrusted input parsed before any signature is checked, envelope bytes scanned plus serialized response bytes share one 16 MiB budget per lookup, and a server refuses writes above 1 GiB per owner or 10 GiB across its artifact cache. Blob bytes have their SHA-512 recomputed before they are returned to the caller, as required above.

The divergence is the shape of the batch. This section specifies one round trip for the whole install, ideally folded into `POST /-/pnpr/v0/resolve`; what shipped is a **20 ms coalescing window** over candidates as each package's files arrive, capped at 512 candidates per request, and no folding into resolve. The reason is that restoration is per package — a package links as soon as its own artifact is in hand — so an install-wide barrier before any lookup would have made every package wait for the slowest fetch to even become a candidate. Which shape actually wins is the benchmark listed as unresolved below, and it is now a question that can be measured rather than argued.

There is also only one channel: the lookup goes to the configured `pnprServer`, not to the registry each package resolved from. Per-channel grouping is specified above and unexercised, since a single-server deployment has nothing to group. That is a narrowing of the proof of concept, not a retraction — the leak argument for grouping stands unchanged the moment a second channel exists.

**Two constraints the implementation added, which belong in the design.** First, a candidate carries its **source tarball integrity**, and the signed payload binds the package name, version, and that integrity. An artifact is therefore not "a build of something whose dependency graph hashes to K" but a build of exactly these source bytes, and a package whose source integrity is not verified is not a candidate at all. Second, because the input key is a hash, the client tracks the `(name, version, source integrity)` identity behind each key within an install: if two different identities appear under one key, the key is ambiguous, and the client stops using it and builds locally. Nothing incorrect could have been restored — the signed payload binds the identity, so a mismatched artifact fails verification anyway — but a key that cannot name one thing has no business being looked up.

**Remote reuse is off under `--ignore-scripts`, and the local cache wins.** Reuse is a substitute for running the build, so it must not resurrect a build the user asked to skip; and when this machine's own side-effects cache already holds an entry for the package, no remote lookup is issued for it.

### Remote artifacts stay labelled once stored

A verified artifact must not become indistinguishable from a locally built one the moment it lands in the store. The store is global and shared across every project on a machine, so an unlabelled remote entry would be silently reused in situations where it should not be: after its signing key was revoked; after remote artifacts were disabled; by a project belonging to a different organization that happens to share the store; or for a package that now resolves through a different registry entirely — which would defeat the owner-scope namespacing this design otherwise depends on.

The existing `sideEffectsMaps` type carries only `added` and `deleted`, so remote entries cannot simply be fed into it and forgotten. Remote artifacts therefore retain **persistent origin metadata**: the owner scope, the signer key identifier, the builder profile, the signed envelope, their verification status, and the channel they were fetched from — the last for diagnostics only, since acceptance turns on the signature rather than on the source.

**Trust policy is applied at every reuse, not only at download.** An artifact whose signing key has since been revoked, or whose owner the current project does not trust — a different organization's trust domain, or a publisher identity this project does not accept — is not reused for this install, and the package builds locally. Reuse turns on the **owner**, not on the channel that originally supplied the bytes: the channel determines where a client looks, and the signature determines what it accepts, so an artifact does not become untrustworthy because the registry it arrived through is no longer configured. The channel is recorded for diagnostics, not consulted for acceptance. It is not deleted: the store is global, and another project may still legitimately trust the same artifact. Whether this is implemented as fields on the existing entries or as a separate local index for remote artifacts is an implementation choice; the requirement is that origin survives storage and is consulted on every use.

**Shipped in v0 by not storing them.** A restored artifact is placed in the in-memory `sideEffectsMaps` of the package being linked, under that machine's local dependency-state key, and is never written to the store index as a local side-effects entry. It is looked up, verified, and hydrated again on the next install. This satisfies the requirement above the one way that needs no new persistence format — an unlabelled remote entry cannot outlive the install, because no remote entry outlives the install — at the cost of paying the lookup every time. The persistent origin metadata specified here is therefore still entirely unimplemented, and it is what has to exist before a remote artifact may be cached locally at all.

Support is negotiated per channel. For a registry channel this is the existing `/-/pnpr` handshake: a registry that does not implement the endpoint says so and the client builds locally, so the feature degrades correctly against `registry.npmjs.org` and every other registry that will never implement it. A publisher channel that is not a pnpr-speaking registry needs no handshake — it is located by the discovery mechanism listed as unresolved below, and its artifacts are accepted on signature regardless of what served them.

### Manifest validation is mandatory

A remote manifest supplies file paths that reach `importIndexedDir` (`pnpm11/fs/indexed-pkg-importer/src/importIndexedDir.ts`). Locally produced side-effect paths come from walking a directory pnpm itself created; remote paths carry no such guarantee. The existing `sanitizeFilenames` helper is a compatibility retry for badly-named files in tarballs — it runs only after an import failure and sanitizes per path segment — and must not be mistaken for a security boundary.

Before any remote manifest is acted on, both clients must reject: absolute paths; any `..` segment; platform-specific separators; NUL and control characters; duplicate paths and paths colliding under case-insensitive filesystems; symlink or special-file entries not explicitly modelled; modes outside an allowed set; and file counts or sizes beyond configured limits. A manifest failing any check is a cache miss and the package builds locally.

This matters more than the equivalent check on tarballs because artifact-publish authority is deliberately weaker and more widely delegated than package-publish authority.

**Shipped in v0, minus quarantine.** Validation runs at the boundary before any remote-supplied path reaches the importer, and a failure is a miss. Quarantine is not implemented: a digest mismatch or a rejected manifest discards the variant for the current install only, so the next install fetches the same bad bytes again. That is the deferred half, and it is deferred together with the persistent origin metadata above for the same reason — both need somewhere durable to write, and v0 writes nothing.

### Trust

The registry that served a package's tarball is already trusted to hand over the code its install script would execute, so serving the built form of that same package is a smaller step than trusting an unrelated cache service. But the step is not zero, and the RFC should not claim it is.

**In a frozen install the lockfile pins the tarball's integrity, so a compromised registry cannot substitute source bytes undetected. No such pin exists for an artifact.** A registry — or anyone it has authorized to upload artifacts — can therefore substitute arbitrary built files without violating any integrity the lockfile records. That is strictly more authority than a registry has today, and `onlyBuiltDependencies` does not cover it: approving a package authorizes running *its* script, not accepting arbitrary output attributed to it by a third party.

This RFC resolves that as follows:

- **Remote artifacts are a separate opt-in, per owner.** `sideEffectsCacheRead` continues to mean the local cache and is not silently widened. A user enables remote artifacts for a named registry, or accepts a publisher's artifacts, deliberately — and that act is the grant of the additional authority described above. The opt-in attaches to the owner whose signature will be trusted, not to the host that happens to serve the bytes.
- **Provenance is signed, not merely recorded.** A signature binds the protocol version, the source tarball integrity, the input key, the builder profile, the compatibility constraints, the manifest digest, the builder identity, and the **owner scope** defined above — the last so that an artifact cannot be replayed outside the scope it was signed for. Unauthenticated provenance fields are useful for debugging and useless against substitution; only the binding makes an artifact attributable.
- **The signing key must be independent of the registry.** This is the load-bearing constraint, not a deployment detail. The threat this section exists to address is a registry — or an uploader it authorized — substituting built files. A registry that signs artifacts itself defends against nothing it is not already trusted for, and reduces the signature to a transport checksum. The signer is therefore a **pluggable trust root**, with two kinds defined as peers: an **organization-configured CI signing key** per registry, held outside the registry server; and **publisher identity**, reusing the trust root that already authenticates the package itself. Key identifiers, rotation, and revocation are part of the shape from the start rather than retrofitted. Neither kind is privileged in the protocol; see the two modes above.
- **Several builders per input key is the normal case.** Two CI pipelines can legitimately produce entries for the same package, profile, and tags. Builder identity therefore participates in variant identity: the registry stores the variants and the client picks one signed by a key it trusts, rather than the registry silently choosing on the client's behalf.
- **The existing allowlist gate is preserved.** A remote artifact is accepted only for a package `allowBuild` already permits. Fetching a prebuilt artifact avoids *rebuilding* something you approved; it is not a route around approving it.

**Shipped in v0.** Signatures are ECDSA P-256 with SHA-256 over the *exact bytes* of the artifact payload, carried base64 in a `SignedArtifactEnvelope` alongside `algorithm` and an opaque `keyId`; verification keys are P-256 SubjectPublicKeyInfo DER. Signing opaque bytes rather than a canonicalized object was a deliberate choice worth recording as guidance for the production protocol: the alternative commits both stacks to agreeing on a JSON canonicalization forever, and any divergence between the Rust and TypeScript canonicalizers is a signature-verification divergence — a class of bug that presents as an install failure on one implementation only. Verification uses the decoded bytes unchanged, so property order and manifest serialization are whatever the signer emitted. The envelope's own digest — the value a lockfile pin will name — is SHA-256 over the domain-separated concatenation `pnpm-shared-artifact-envelope-v1\0algorithm\0keyId\0payload\0signature`, and so is defined independently of how any of it was serialized. The signed payload binds package name and version, source tarball integrity, owner scope, input key, and compatibility constraints, all of which must match the candidate; the input key's `dependency-side-effects:v1:` prefix is inside the signature, so the domain separation this document asks for is enforced rather than conventional.

The independence constraint holds in the shape that matters: the client verifies against `trustedKeys` it was configured with out of band, never against anything the server supplies, so a pnpr that served the bytes cannot make itself their signer. The `allowBuild` gate is confirmed on the remote path — a candidate is only ever submitted for a package `allowBuild` already permits. What is *not* settled is the rest of the key lifecycle: distribution in v0 is "put the base64 public key in the environment", and rotation and revocation have no mechanism at all, which is one of the two things that keep this opt-in.

### Artifacts are mutable authority over an immutable release

A published tarball is immutable: `foo@1.2.3` has one set of bytes forever, and the lockfile pins their integrity. Artifacts break that symmetry, and the consequence is severe enough to state plainly.

**An artifact can be published long after the release it applies to.** If a publisher's credentials are compromised in 2027, the attacker can sign a new artifact for `foo@1.2.3` — a version published in 2026 whose tarball integrity in your lockfile still verifies perfectly. A frozen install would then accept attacker-built binaries for a version pinned years earlier, with nothing in the lockfile changed. The same holds for a compromised organization key over its own domain. This is a genuine loss relative to the guarantee npm otherwise provides, and no amount of signing fixes it, because the signature would be valid.

Two positions are available, and the RFC takes both in layers:

- **Pin on first use.** When a client accepts an artifact, it records the **digest of the complete signed envelope** in the lockfile, keyed by input key and owner, exactly as it records tarball integrity.

  The pin must cover the envelope, not the file manifest. Compatibility tags, owner scope, and provenance are signed alongside the manifest rather than being part of it, so pinning the manifest digest alone would leave a compromised signer free to re-sign *the same bytes* with broadened compatibility claims — an artifact honestly tagged `glibc >= 2.31` re-issued as `glibc >= 2.17`, and thereafter selected on systems where it will fail. Only the envelope digest fixes what the artifact claims about itself as well as what it contains.

  A lockfile is shared across platforms, so several variants may be pinned for one input key — but a flat *set* of digests is not enough. A set cannot distinguish a platform that was never pinned, where an unpinned artifact should be accepted, from a platform whose pinned artifact has been replaced, where the substitute must be rejected: both present as "this digest is not in the set".

  The pin is therefore a **map from a canonical consumer platform fingerprint to an envelope digest**. The fingerprint is the hash of the consumer's own **canonically ordered supported-tag set, together with the tag-schema version** — not an informal OS/architecture tuple, which would silently omit Node ABI, libc, CPU baseline, and every compatibility dimension added later. Defining it over the tag vocabulary means the fingerprint gains new dimensions exactly when the vocabulary does, and the schema version makes a vocabulary change a visible repin rather than a silent collision. It is computed from the consumer's identity rather than from an artifact's advertised tags because tags are floors: several artifacts may match one consumer, so only the consumer's own identity is a stable key. Lookup is then unambiguous: a fingerprint present in the map pins that platform, and any other envelope is rejected; a fingerprint absent from the map is a platform this project has not pinned, and the unpinned rules below apply. Two consumers on different platforms may legitimately pin the same digest under different fingerprints, which costs an entry and buys the distinction.

  **Pins accrue on lockfile-writing installs.** A frozen install does not modify the lockfile and therefore records nothing; an artifact whose fingerprint is absent from the map is accepted on signature alone, exactly as in the unpinned case below. Pins for the platforms a team actually develops on are committed by ordinary installs and protect CI thereafter; a platform only ever seen in CI stays unpinned until someone runs a non-frozen install there. Refusing unpinned artifacts on frozen installs was considered and rejected: it would disable the feature precisely where it is most valuable.

  **Replacing a pin is explicit and reviewable.** A pinned fingerprint rejects every other envelope, which is the point — but signer rotation, an evicted-and-rebuilt artifact, and a corrected build are all legitimate reasons to want a different one under an unchanged input key, so there must be a way to say so. Three paths exist, and only the last is a repin:

  - The input key changes — a dependency update, a new patch — and a fresh pin is recorded under the new key with no user action, which covers the common case.
  - The tag-schema version changes, which changes every fingerprint and repins as a visible lockfile diff.
  - The user asks, through an explicit lockfile-writing operation (`pnpm install --refresh-artifact-pins`, optionally filtered to particular packages) that drops the selected pins so the next acceptance records new ones.

  Silent automatic repinning is deliberately excluded: a pin that any ordinary install may rewrite protects nothing. Because pins live in the lockfile, every replacement appears in the diff and can be reviewed, which is most of what makes them worth having. Note that a revoked signer needs no repin to be *safe* — trust policy rejects its artifacts before the pin is consulted and the package builds locally; repinning is how the cache is re-enabled afterwards, not how safety is restored.

  **A pinned artifact that is no longer available falls back to a local build**, with a diagnostic, rather than failing the install — an artifact is an optimization over building, and the package remains buildable from source. The honest caveat is that a consumer who cannot build locally at all, such as a container without a toolchain, will still fail, only later and with a worse message than a dedicated error would give.
- **Explicit trust for the unpinned case.** A platform not yet seen has no pinned digest — a new contributor on a different OS, or a publisher legitimately adding a target after release. There the artifact is accepted on signature alone, which is mutable authority, and the RFC does not pretend otherwise. This is the same property PyPI has, where wheels may be uploaded to an existing release, and it should be a documented consequence of opting in rather than a surprise.

An artifact index digest published as part of immutable release metadata would be stronger than either, since it would fix the valid set at publish time. It is not proposed here because it forecloses adding a platform after release, which is a thing publishers legitimately need to do — but it is the right answer if the ecosystem ever wants the stronger guarantee, and the format should leave room for it.

**Shipped in v0: the fingerprint, not the pin.** `platformFingerprint` exists and is computed identically in both stacks — SHA-256 over `pnpm-platform-fingerprint-v1\0` followed by each canonical supported tag in preference order with a NUL byte after each, rejecting duplicate tags and lists longer than 64 entries. So the value the lockfile map would be keyed by is defined, byte-identical across the two implementations, and already carries the tag-schema version by construction. The map itself, and `pnpm install --refresh-artifact-pins`, are deferred.

Until they land, v0 is *entirely* the second arm of this section: every accepted artifact is accepted on signature alone, and the mutable-authority exposure described above is the whole of the feature's guarantee rather than its edge case. Stated plainly: a compromised organization signing key can serve attacker-built binaries for a dependency version pinned years earlier, and nothing in a v0 install would notice. That is a defensible position for an opt-in proof of concept whose users configured the key themselves; it is not a defensible position for anything enabled by default, which is why lockfile pinning is the first item on the remaining-work list rather than a refinement.

### Publishing

Writing artifacts is a separate grant from publishing packages, with its own policy verb. "May publish `foo`" and "may publish a build of `foo`" differ in kind: a package is reviewed source, a build is the output of an install script. Publication is opt-in per registry and off by default. In organization mode the expected deployment is a team's own registry populated by that team's CI; in publisher mode the grant belongs to whoever may publish the package itself, and the same distinction applies — a token that may publish `foo` does not thereby gain the right to publish builds of it.

**Shipped in v0, together with a rule this document had not stated.** Configuration is split by who owns each half, and the split is enforced rather than recommended. A repository declares only *what* is eligible — the owner `organization` and the `packages` allowlist — in `pnpm-workspace.yaml`. Everything describing *the act of signing* — `publish`, `keyId`, `privateKey`, `trustedKeys`, `builderId`, and the provenance fields — is refused in the workspace file, with `ERR_PNPM_WORKSPACE_REMOTE_SIDE_EFFECTS_TRUST`, and read only from the machine's global config file or the environment. The feature applies only when both halves are present.

The reasoning generalises well beyond the proof of concept and should survive into the production protocol: **a committed file is not a trust root.** If `pnpm-workspace.yaml` could name the signing key or turn publication on, then cloning a repository onto a builder that holds a key would turn that builder into a signing oracle for whatever the clone asked to have signed — and the trusted-key list would be attacker-controlled input to the verification it is supposed to anchor. The repository names its own policy; the machine holding the key decides whether it signs.

Publication captures the actual post-build diff produced by that builder, so what is uploaded is what the build did rather than a re-derivation of it, and it is off unless explicitly enabled on that machine.

### What pnpr already provides

The design reuses pnpr's routing and storage model rather than adding a parallel one.

- **Private-entry namespacing.** `RoutePolicy` already namespaces private resolution-cache entries under an HMAC keyed on `resolution_cache_secret` so they are not correlatable offline. The mechanism carries over — but **its input does not.** Source visibility must not determine artifact scope: a public source package built by one organization still yields an artifact that can reveal builder identity, embed organization-specific output, or simply differ from another organization's build of the same public package. Artifacts are therefore namespaced by their **owner scope**: organization-owned artifacts under the owning organization, publisher-owned artifacts under the package identity they belong to and shared across every consumer. Publishing an organization's artifact beyond its namespace is a separate explicit decision, never a consequence of the source tarball having been public.
- **Durability.** Artifacts are regenerable derived data: obtainable again from the tarball plus a build, safe to wipe, self-healing. (Regenerable, not reproducible — a rebuild need only be behaviourally equivalent.) That is the contract of pnpr's disposable `cache` root as distinct from the authoritative `storage` root, so artifacts need no new storage tier. The existing S3 block remains available for operators who want them shared across replicas.
- **Per-package policy.** "Serve artifacts for `@ourco/**`, never for `**`" is a `packages:` pattern rule using the existing specificity selection.
- **Existence is not leaked.** `access` already gates reads with denied callers masked as not-found, which matters because artifact existence would otherwise reveal an organization's dependency graph and input keys.

**Shipped in v0.** Artifacts live in the disposable `cache` root, namespaced by owner, exactly as this section anticipates — no new storage tier was needed. What the design did not anticipate is how much of the work a *write* endpoint is: v0 adds transactional per-owner and global storage accounting, a cross-process filesystem lock so that pnpr processes sharing one cache enforce the eight-variant-per-key cap together rather than each independently, and bounds on request and response size, timeouts, streaming memory, manifest size, variant count, descriptor count, lock namespaces, concurrency, and crash residue. Reusing the storage model was cheap; accepting untrusted uploads into it was not, and a second implementation of this protocol should expect that cost rather than discover it.

### Forward compatibility with a workspace task cache

This RFC caches the build output of *dependencies*. The obvious later use of the same machinery is caching the output of a workspace's own *tasks*, in the manner of Turborepo, Nx, and moon. That is not proposed here and is not a dependency of anything below — but most of what this RFC specifies is general, and a few decisions would foreclose the reuse if made carelessly. They are recorded as decisions rather than left to accident.

What would transfer unchanged: the `{added, deleted}` manifest over CAS blobs (a task output is the degenerate case — a file set with no base tree and no deletions); the batched per-channel lookup and its folding into an existing round trip; signed provenance; owner scope, where a task cache is always `organization` and the `publisher` arm simply goes unused; trust policy re-evaluated at every reuse; blob digest verification and quarantine; and manifest path validation, which matters *more* there, since task outputs land in a working tree rather than in the store. The build-input argument in this document is likewise the same argument Turborepo's `inputs` and `env` declarations exist to answer.

What would be new is the key: this RFC derives an input key from the lockfile, while a task key is source content, task configuration, environment, and upstream task keys. That is additive — a different key producer feeding the same storage and transport — rather than a change to anything specified here.

Three constraints follow, all cheap now and breaking later:

- **Entry keys are opaque but domain-separated.** The protocol must not embed package identity in the shape of a request or response key — a request assuming `(package, version)` cannot carry `(project, task, hash)`. Keys are therefore strings the client computed and the server stores, prefixed with the artifact kind and version (`dependency-side-effects:v1:…` against a future `workspace-task:v1:…`), and the signed envelope binds the kind. Without both, a party able to publish one kind of artifact could target the other's keyspace.
- **Task restoration would need declared output roots.** The path validation specified above is necessary but not sufficient for a task cache: dependency artifacts land in a directory pnpm owns, while task outputs land in the user's working tree. Restoration must additionally be confined to the output roots the task declared, so a cache entry cannot write outside them even with individually well-formed relative paths.
- **Compatibility must stay expressible for platform-independent output.** Constraints are load-bearing for a native module and vacuous for a `tsc` build, but the vacuous case is expressed by asserting `universal`, never by omitting the field. A task cache uses `universal` for outputs that genuinely are; it must not acquire a third, implicit state in which missing constraints are read as unconstrained.
- **The endpoint is named for the mechanism, not for this use.** `side-effects` names one application of a general artifact cache. Either the name generalises, or a task cache adds a second endpoint doing the same thing for no reason. **Shipped in v0** as `/-/pnpr/v0/artifacts{,/resolve,/blob}` carrying opaque client-computed keys, so this constraint is honoured on the wire; the *client* setting is still named `remoteSideEffectsCache`, which is the narrower name and would need a companion rather than a rename if task caching ever arrives.

Worth noting as a byproduct rather than a goal: because pnpm's store is content-addressed at file granularity, a task cache built on it would deduplicate identical files across tasks, packages, and dependency artifacts in one store. Turborepo stores each task's output as its own archive, so a file present in ten outputs is stored ten times. That advantage comes from infrastructure pnpm already has, not from anything designed here.

## Rationale and Alternatives

**An external package provider ([pnpm/pnpm#13639](https://github.com/pnpm/pnpm/pull/13639)).** Delegate materialization of every package to a third-party executable, optionally backed by the Nix store. This delivers shared build outputs, at the cost of a permanent stdio protocol, a second install mode incompatible with the global virtual store, the pnpr server, and the hoisted linker, and the silent voiding of `onlyBuiltDependencies`, `--ignore-scripts`, and `approve-builds` because the provider decides what builds. It also serves only users who have already adopted Nix. Notably, it does *not* escape the build-input problem — it relocates it into the provider, where Nix's restricted build environment is what actually solves it. This RFC bounds the problem instead, via a trust domain, compatibility constraints, and eligibility.

**A standalone cache URL, in the shape of Turborepo's Remote Cache.** A `sideEffectsCacheUrl` pointing at a dedicated service. This is **subsumed rather than rejected**: once channels are non-authoritative and acceptance turns on the signature, a dedicated cache service is simply another channel, and the design already permits arbitrary ones. An earlier draft rejected it on the grounds that it introduced a new principal permitted to write into `node_modules`; that objection does not survive signature-based acceptance, and is withdrawn.

What remains is a question of default rather than of permission. Reaching artifacts through the registry a package resolved from means tokens, helpers, certificates, and proxies already work, and the registry-qualified lockfile keys already say where to look — so registry attachment is the better *default*, and a standalone service is the configuration a user chooses when they have one. It is worth noting the same reasoning is what makes publisher mode workable at all.

**Adopt the Bazel Remote Execution API v2 instead of defining a protocol.** REAPI is a real standard with off-the-shelf servers (bazel-remote, Buildbarn, BuildBuddy), and moon adopted it after sunsetting its own hosted cache. It covers more than it first appears: `Platform` properties are explicitly intended for "hardware, operating system, or compiler toolchain" and are implicitly part of the Action digest; `ExecutedActionMetadata` records the producing worker; `GetActionResult`/`UpdateActionResult` work without the Execution service; and because `Command` declares which outputs are captured, an `ActionResult` need not carry a full tree — pnpm's added-file set could be declared directly as outputs.

It is declined on a single objection, which is sufficient on its own: **its lookup model is exact-digest, and this design requires compatibility selection.** `GetActionResult` answers "is there a result for precisely this Action digest". It cannot answer "give me the best artifact compatible with this ordered tag set, signed by a key I trust" — which is the question a floor-based tag model with multiple builders must ask. Emulating it means the client enumerating one candidate digest per supported tag in preference order and issuing a lookup for each, multiplying request count by tag-set size, in a service with no batched `ActionCache` read at all (`GetActionResultRequest` carries a single `action_digest`; only the CAS service batches). `Platform` property matching does not rescue this: it governs execution placement, not cache lookup, which stays exact-digest regardless.

One narrower mismatch is worth recording but is not load-bearing: `Action` requires a `command_digest` referencing a `Command` in CAS, while pnpm has no command, so the key would derive from a synthesized `Command` no worker can execute, making its canonicalization an unintended compatibility surface. Deletions, by contrast, are *not* an obstacle — a pnpm manifest carrying its own `deleted` list can be stored as a single opaque `ActionResult` output blob, since CAS contents are uninterpreted.

Raw round-trip count is deliberately *not* claimed as the deciding factor. gRPC multiplexes concurrent RPCs over HTTP/2, so N lookups are not N serialized round trips, and whether batching wins on wall-clock is a question for measurement rather than assertion. A hybrid — REAPI's CAS and action cache with a small batched-lookup extension — is a coherent option and is the most likely route back to this alternative, along with a batched `ActionCache` appearing upstream.

**Do nothing.** Native module builds stay per-machine. Survivable, and it is the status quo, but it leaves a real cost on every CI run and leaves the Nix-shaped proposals as the only answer for teams that care.

## Implementation

**`pnpm/pnpm` (TypeScript CLI and pacquet).** Split the dependency-state key into an input key and advertised compatibility constraints — this is the largest client change and the one everything else depends on. Record the builder profile as signed provenance, deliberately outside the key. Then a remote tier on the side-effects lookup, grouped per channel. This cannot simply feed the existing `sideEffectsMaps` path unchanged: that type carries only `added` and `deleted`, so remote entries need persistent origin metadata alongside them (or a separate local index), and the reuse path needs a trust-policy check it does not have today. Lockfile support for pinning accepted artifacts on first use — a map from canonical consumer platform fingerprint to signed-envelope digest, per input key and owner — is a further client change, and touches the lockfile format. The fingerprint is a hash over the canonically ordered supported-tag set plus the tag-schema version; that canonicalization is part of the lockfile format and must be byte-identical across both stacks, since a divergence would make the two produce different pins for the same machine. The explicit repin path needs a CLI surface in both as well. Manifest validation must sit at the boundary, before any remote-supplied path reaches the importer. The `allowBuild` gate at `pnpm11/building/during-install/src/index.ts:111` must be confirmed to cover the remote path, not just the local one. Both stacks, per the repository's parity rule.

**`pnpr`.** The batched endpoint on the existing resolver surface alongside `/-/pnpr/v0/resolve`, capability-advertised through the `/-/pnpr` handshake, ideally answerable within a resolve response. Storage in the disposable `cache` root, namespaced by owner scope — per organization for organization-owned artifacts, per package for publisher-owned ones, which are shared across tenants by design. Reuse of `RoutePolicy` and `packages:` rules. A publish path with its own policy verb and signature verification, and the ability to serve publisher-owned artifacts it did not itself accept for publication.

**Documentation.** The protocol, the tag format, and the provenance block are a public contract from the moment they ship and must be specified so registries other than pnpr can implement them.

Ordering: the input-key/compatibility split is the prerequisite, and its format is set by publisher mode's requirements even though organization mode is expected to ship first. Nothing may cross a machine boundary before it exists, because until then the cache cannot state what an artifact is valid for.

### What v0 landed

[pnpm/pnpm#14171](https://github.com/pnpm/pnpm/pull/14171), in both stacks, released in pnpm v12.0.0 with pnpr 0.1.0-alpha.8. The ordering above held: the split went first.

- The input-key/compatibility split, as `calcDepStateInputKey` producing `dependency-side-effects:v1:deps=<graph hash>[;patch=<hash>]` with host identity excluded and advertised by the artifact instead.
- The signed envelope, the v0 tag vocabulary, and the platform fingerprint, shared between a `shared-artifact-protocol` crate and its TypeScript counterpart so the two stacks cannot drift on the bytes that matter.
- The remote tier on the side-effects lookup, batched, and gated on eligibility, `allowBuild`, verified source integrity, and `--ignore-scripts`.
- Manifest validation at the boundary, ahead of the importer.
- Publication of the real post-build diff from a builder explicitly configured to sign.
- On pnpr: the three `v0` artifact endpoints behind `resolver.artifacts`, owner-namespaced storage in the `cache` root, and the accounting and bounds an untrusted write endpoint needs.
- The `remoteSideEffectsCache` setting, assembled from the workspace file, the global config file, and the environment, with the trust material refused in the workspace file.

### What is left, in the order it blocks things

- **Lockfile pinning and the repin path.** The largest remaining item and the one that decides whether this can ever be more than opt-in: until pins exist, every acceptance rests on mutable authority. The fingerprint half is already built.
- **Persistent origin metadata and quarantine.** Without them a remote artifact cannot be cached locally between installs, and a poisoned blob is re-fetched on every one.
- **Key distribution, rotation, and revocation.** v0 distributes public keys by environment variable and has no revocation at all.
- **Publisher mode.** Discovery, the attestation subject, and the authorization policy for who may attest artifacts on a package's behalf. The wire format already carries the owner arm.
- **Platforms beyond Linux/glibc.** The macOS vocabulary is specified above. Windows and additional Linux libc families still need their own compatibility boundaries before implementation.
- **Multi-channel lookup.** Specified above, unexercised: a single-server deployment has no second channel to group by.
- **The batching benchmark**, which now has a real implementation to measure instead of two assertions.

## Prior Art

**`prebuild-install` and `node-pre-gyp`** are the closest prior art of all, because npm already has a publisher-published binary cache — implemented as postinstall scripts that download artifacts from GitHub Releases or S3. It is ubiquitous, which is the strongest available evidence that the demand is real. It also has no lockfile integrity pinning for what it downloads, no signatures, a hard requirement for network access at install time, and it fails under `--ignore-scripts` and offline installs.

**`prebuildify`** is the ecosystem's answer to those failures and is instructive for the opposite reason: it ships every platform's binaries *inside* the published tarball, so nothing is downloaded during installation and the package works with scripts disabled. It buys correctness by making every consumer download binaries for platforms they will never use. That trade — bundle everything, or fetch unverifiably at install time — is the choice a signed artifact channel exists to remove.

**Turborepo and Nx** cache first-party task outputs over a plain HTTP API anyone can self-host, with optional HMAC-SHA256 artifact signing and verification failure treated as a cache miss. Two lessons carry over: a documented HTTP spec is sufficient for a healthy ecosystem of implementations, and treating verification failure as a miss rather than an error is the right default.

Most instructive for this design: **none of the three models the build environment at all.** They can omit it because their caches are team-scoped and their artifacts first-party — the organization already owns their correctness, and no one is defending against another organization having built something wrong. That is the precedent for keeping the builder profile out of the input key here, and for requiring every artifact to carry a named owner rather than admitting an anonymous public cache the environment model would then have to carry.

The analogy breaks in two places. Their threat model is a compromised cache operator or transport, which signing answers because the key never leaves the user's machines; ours additionally includes an artifact that is the legitimate output of a third-party install script nobody read. And their cache keys are user-declared in configuration, so a wrong key is user misconfiguration costing a stale build — pnpm computes the key on the user's behalf, which is why the residual build-input risk is pnpm's to bound rather than the user's to notice.

**moon** ran its own hosted cache service, Moonbase, then sunset it and implemented REAPI so users could run off-the-shelf servers. This is a JS-ecosystem tool that built a bespoke protocol and walked it back, which is why the REAPI alternative is argued rather than dismissed.

**Python wheels** are the closest analogue: the one mainstream ecosystem that made the built form of a third-party dependency a first-class distributable, served from the same index under the same authentication as source. Its compatibility-tag model — the artifact advertises what it is valid on, the installer selects from an ordered set of tags it supports — is the direct model for the tag design here, and manylinux's encoded glibc floor is the worked example of getting a floor right.

**Nix binary caches and Homebrew bottles** achieve stronger guarantees by making builds reproducible and sandboxed by construction, and by signing substituter output. pnpm can assume neither of npm install scripts. That is why this RFC bounds rather than closes the problem, and why every artifact must trace to a named owner who accepts the residual risk — an organization for its own builds, a publisher for its own releases. Bounding is honest only where someone owns the remainder, which is also why the anonymous multi-builder case stays out of scope.

## Unresolved Questions and Bikeshedding

Answers below marked *v0* are what the proof of concept chose, which settles them for organization mode without settling them for the production protocol.

- **Who runs the builds.** If a team's CI builds and uploads, this RFC's scope holds. If pnpr builds, pnpr becomes a build service — that is remote *execution*, which this RFC does not propose, and it is REAPI's actual domain. The distinction should be decided deliberately rather than arrived at. *v0: decided the first way.* A builder is an ordinary `pnpm install` with publication enabled; pnpr only stores and serves, and has no build capability. Nothing in the shipped protocol pulls toward the second reading.
- **Who asserts eligibility, in practice?** Publisher, registry operator, and consuming organization are all plausible, with different incentives. A publisher-asserted flag is the easiest to ship and the easiest to get wrong. *v0: the consuming organization*, through the `packages` allowlist in its own workspace file, which is the only one of the three that needs no new authority anywhere. It is also the one that scales worst, since every consumer maintains its own list — so this stays open for publisher mode rather than being answered by it.
- **Attestation subject and authorization policy for publisher mode.** Reusing publisher identity avoids a new root of trust but not the specification work: trusted publishing authenticates CI to the registry and provenance attests a *package* build, so an artifact needs its own attestation subject and a policy for who may attest artifacts on a package's behalf.
- **Artifact discovery in publisher mode.** Signature-based trust means artifacts may be served from anywhere, which removes the dependency on any registry cooperating but leaves the question of how a client learns where a publisher's artifacts live: a manifest field, a well-known convention, registry advertisement, or several. This is the main unspecified piece of publisher mode.
- **Beyond libc.** Compiler and C++ standard library identity may matter for some native modules and not others. Since the profile is not a gate, the question is whether any of it needs to become a compatibility tag, or whether it is eligibility's job. Untouched by v0, whose vocabulary covers libc and nothing else; extending it is a schema-version bump, which is the mechanism working as intended.
- **Non-relocatable builds.** Some builds embed absolute paths or host state and are never shareable. Detection, a `package.json` marker, or eligibility-by-default-off? [pnpm/pnpm#5002](https://github.com/pnpm/pnpm/issues/5002) asks for the local form of this.
- **Sandboxed and unsandboxed artifacts.** If dependency scripts eventually run sandboxed ([pnpm/pnpm#13772](https://github.com/pnpm/pnpm/issues/13772)), provenance records which produced an entry — but whether a client should accept the other kind is a policy question.
- **Key distribution.** V1 fixes the shape — one organization-configured CI key per registry, held outside the registry server, with identifiers, rotation, and revocation. How a client learns and pins those keys, and whether revocation needs to be online, is not settled. That a registry may *not* sign on a builder's behalf is settled, and is stated in the trust section rather than here. *v0 ships the weakest thing that is still honest:* a `keyId`-to-public-key map from the global config file or the environment, and no revocation. The identifiers are in the format, so revocation can be added without a format change — but a design in which trust is revoked by editing every consumer's environment is not one to ship on by default.
- **Batching versus concurrent lookups.** The batched design should be benchmarked against concurrent per-package lookups over HTTP/2 rather than assumed faster, including at small candidate counts where a single request may not pay for itself. v0 makes this measurable and adds a third option to measure: its 20 ms coalescing window is neither the install-wide batch this document specifies nor a request per package, and it was chosen to keep per-package restoration from serializing behind an install-wide barrier. Whether the window is worth its latency at small candidate counts is exactly the open question.
- **What an ambiguous input key should mean.** Two distinct `(name, version, source integrity)` identities hashing to one input key is a contradiction rather than an attack — the signed payload binds the identity, so nothing wrong can be restored — but it means the key does not name one thing. v0 stops using such a key for the rest of the install and builds locally. Whether the production protocol should instead prevent the case, by binding package identity into the key's domain separation, is worth deciding before a second artifact kind shares the keyspace.
- **Inline small files.** Whether small files ride inline in the batch response instead of costing a second blob fetch is measurable and should be measured.
